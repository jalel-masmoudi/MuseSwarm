### Short Description / Tagline
> **MuseSwarm** is a multi-agent bot-to-bot software engineering platform powered by Meta's open-weight `Muse Spark Open` (`meta-models/muse-spark-open-1026`) on Baseten (2M TPM) and integrated into Cursor IDE via MCP. Four specialized peer bots (`@architect`, `@builder`, `@verifier`, and `@lead`) negotiate specs over a live session message bus, track dependencies on an auditable Kanban board, execute sandbox runtime tests (`node test.js`), and autonomously self-heal defects in a rework loop until verification passes.

### Full Technical Description (Impact, Use of Meta AI Tooling, Technical Depth & Execution)
1. **Problem & Impact (30%):**
   Single-agent coding assistants often drift in scope or ship untested code because the same context writes both the specification and the implementation. Meanwhile, Meta's new `Muse Code` CLI introduces multi-agent session messaging, but native session messaging is unavailable on Windows and requires manual multi-terminal setup. **MuseSwarm** bridges this gap across Windows, macOS, and Linux by orchestrating four specialized `Muse Spark Open` agents with strict role separation and automated sandbox verification.
2. **Use of Meta AI Tooling (25%):**
   - Powered by **`meta-models/muse-spark-open-1026`** on **Baseten** (`https://inference.baseten.co/v1`, up to 2M TPM), extracting and surfacing `Muse Spark Open`'s internal chain-of-thought (`reasoning_content`) alongside structured peer messages.
   - Implements Meta's **Multi-Agent Orchestration Contract** (`profiles/*/SOUL.md`, `brief.md`, `runbook.md`, and `AGENTS.md`): `@architect` owns the spec and Kanban board without touching code; `@builder` implements isomorphic modules (`app.js`), interactive UI (`index.html`), and unit tests (`test.js`); `@verifier` runs real sandbox checks (`node --check` + `node test.js`) and triggers multi-turn rework loops with stack traces; `@lead` synthesizes documentation and `benchmark.json`.
3. **Technical Depth & Execution (20%):**
   - **Resilient Baseten Inference Client (`src/baseten-client.js`):** 45s default `AbortController` timeouts, 120s for file-bearing `@architect` / `@builder` / `@lead` calls, exponential backoff + jitter + `Retry-After` handling on HTTP 408/429/5xx, optional `reasoning_effort` (dropped for the rest of the run if Baseten 400s it), rolling 60s TPM/RPM window tracking, p50/p95 latency percentiles, and per-agent token breakdown. `benchmark.json` telemetry is scoped to that session; `/api/status` still reads process-wide totals.
   - **Dependency-Aware Kanban & Parallel Fan-Out (`src/swarm-engine.js`):** Supports `steer`, `queue`, and `notify` delivery modes, DAG task dependencies (`dependsOn`), parallel task fan-out (`runParallelTasks`), a 100-point automated quality rubric, and autonomous `@verifier -> @builder` self-healing rework loops. Each workspace write snapshots `fileHistory`. A Pass 1 → Pass 2 heal stores a unified diff (`-` broken line, `+` healed line, before/after snippets) on `reworkDiffs`, the session payload, and `benchmark.json`, served at `GET /api/session/:id/diffs`.
   - **Three judge scenarios (`src/scenarios.js`):** `sprint-priority-engine` (weighted incident scoring + SLA detector), `feature-flag-rollout` (FNV-1a bucketing + canary circuit breaker), and `oncall-fairness-scheduler` (timezone handoffs + Jain fairness rebalance). Each emits `domain.js`, `app.js`, `test.js`, and a dark-mode `index.html` that pass `node --check` and `node test.js` after the self-heal. `GET /api/scenarios` lists them.
   - **Triple Interface:** Terminal CLI (`node src/cli.js doctor | peers | run --demo | run --scenario <id> | benchmark`), Real-Time SSE Web Studio (`http://localhost:4321` with judge scenario presets, a Pass 1 → Pass 2 self-healing diff, multi-file artifacts, live `reasoning_content`, Kanban, and an embedded live app preview), and a 4-tool **Cursor MCP Server** (`src/mcp-server.js`) the studio calls through `POST /api/mcp/invoke` (`muse_swarm_list_agents`, `muse_swarm_ask_agent`, `muse_swarm_cobuild`, `muse_swarm_telemetry`).
4. **Live Verification Results (25%):** from the committed live Baseten reference run `workspaces/sprint-priority-engine-8z24/benchmark.json` (`mode: live-baseten`, session `swarm-mvskiwfb-8z24`).
   - **Rubric Score:** `98/100 (VERIFIED_PASS)` (Correctness `25/25`, Test Coverage `24/25`, Architecture Adherence `25/25`, UI Completeness `24/25`, `8` asserts in `test.js`).
   - **Sandbox Checks:** `4/4` checks passed (`syntax:app.js`, `syntax:test.js`, `runtime:test.js`, `artifact:index.html`). The same run's `.session.json` records 5 `[PASS]` suites in `node test.js` and a `675ms` verification.
   - **Verification Runs:** `1` run, `0` rework cycles (`verification.runsCount = 1`, `reworkCycles = 0`): this live run passed on Pass 1.
   - **Self-heal accounting:** each rework cycle records one failing Pass 1 verification (`phase: pass1_initial`) and one passing Pass 2 verification (`phase: rework_verify`). For example, offline `POST /api/swarm/rework` on a judge scenario gives `reworkCycles = 1`, `verification.runsCount = 2`, `failedRuns = 1`, `passedRuns = 1`. If `@builder`'s patch changes the file but still fails, that run stays as `rework_verify` (failed) and the engine's restore is verified separately as `restore_verify`. A `fallback_verify` run appears only if every rework attempt fails. Each run is labelled with `run`, `pass`, `phase`, `reworkAttempt` and `candidate` in the session payload and in `benchmark.json` (`verification.runs`).
   - **Who heals Pass 2 (honest note):** there are two heal paths. (1) **`model`**: `@builder` gets the failing test output plus the files the stack trace and their `require()` chain point at (including `domain.js`), and returns a `{files:[{path, content}]}` patch. The engine applies it only if it changes a file, and keeps it only if `node test.js` then passes. (2) **`deterministic_restore`**: if the reply has no usable patch, an unchanged patch, or a patch that still fails, the engine restores the saved pre-fault source itself. Every write is logged with `author` and `source` (`model`, `offline_fixture`, `scenario_fixture`, `fault_injection`, `deterministic_restore`, `engine_fallback`, `engine_summary`) in `fileHistory`, `reworkDiffs` (`source`, `fixedBy`, `verifiedPass`), the session payload, SSE `file_written` events and `benchmark.json` (`healedBy` per cycle, `reworkSummary`, `fileAttribution`). `@builder`'s raw rework reply (content and `reasoning_content`) is stored in the session's `modelReplies` and streamed on SSE `llm_complete`. Offline runs always show `deterministic_restore`. In live Baseten runs on this head, Muse Spark fixed `domain.js` itself in 2 of 3 scenarios (sprint-priority-engine, feature-flag-rollout) and the sandbox verified it with the fixture tests and an isolated grade. In oncall-fairness-scheduler its fix reintroduced a sorting bug; the direction test caught it and the engine restored the clean file (healedBy: deterministic_restore). A parsed `@builder` build writes `app.js` / `index.html` as `model` only if `app.js` `require('./domain.js')`; otherwise it is `rejected_contract` and the fixture is used. In scenario mode `test.js` is engine-owned grading: model writes are recorded as `rejected_protected_file` (never `model`), the fixture tests are restored before every `node test.js`, and the rework prompt lists `test.js` as read-only. Scenario rework may only patch the seeded fault file (`domain.js`); `app.js` shims are `rejected_non_target`. A heal is credited to `model` only if an isolated child-process grade of `domain.js` matches the fixture (no shared `assert`); static `assert`/`process`/`require.cache` shims are `rejected_grading_check`. Failures revert and `deterministic_restore` writes every scenario code fixture that is not a kept model `app.js`. The same isolated grade gates Pass 1 `VERIFIED_PASS`. A session is `VERIFIED_PASS` only if a verification run actually passed (and the isolated grade passed); otherwise `VERIFIED_FAIL` with verification points zeroed so the score cannot look like a pass. Rework uses 32k tokens, `reasoning_effort=low`, a compact fault-file prompt, and retries once on empty `finishReason=length`. Omitted files (always `domain.js` in the judge prompts) and truncated builds stay `scenario_fixture`. `@lead` and the initial `@builder` build retry once if `finishReason=length` leaves no usable content, with `reasoning_effort=low` and a 32k (`@builder`) / 16k (`@lead`) token cap, before any engine fallback. `benchmark.json` telemetry (calls, tokens, latencies, p50/p95) is scoped to that session.

The parser of that time could not read the `@architect`, `@builder` and `@lead` replies, so `brief.md`, `runbook.md`, `app.js`, `test.js`, `index.html` and `README.md` there are the engine's built-in fallback files.
